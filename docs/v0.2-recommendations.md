# V1 Recommendations

Goal: a publishable 1.0 of this crate. Primary target is vocal processing on the Daisy
Seed (STM32H7, `no_std`, no allocator), but the library should work platform-agnostic —
desktop (CPAL/JUCE-style hosts, nih-plug), other MCUs, WASM.

Reviewed 2026-07-05 at commit `2d33801` (plus uncommitted changes in `effects/` and
`vocal_effects.rs` — commit or stash those before restructuring).

## What's already right

- `no_std` core with zero allocation — the hard part of platform-agnosticism is done
- Const-generic FFT sizes (512–4096) with a single generic implementation behind them
- `sample_rate` is a config value, not a constant — no hidden 48 kHz assumptions in lib
  code
- microfft is a good FFT choice for `no_std`; builds clean with `--no-default-features`
- Host test suite passes; criterion + hound already in dev-deps

## 1. API: move state into a processor struct (the big one)

The current entry point makes the caller own all DSP state and thread it through a
9-argument free function:

```rust
process_vocal_effects_1024(&mut buf, Some(&mut carrier), &mut in_phases,
    &mut out_phases, &mut env, &mut inv_env, prev_ratio, &config, &settings)
```

Problems: callers can mix state arrays between instances, `previous_pitch_shift_ratio`
must be manually threaded (the firmware currently passes a value it never updates),
and every internal state addition is a breaking API change.

V1 shape:

```rust
pub struct VocalProcessor<const N: usize> { /* phases, envelopes, prev ratio */ }

impl<const N: usize> VocalProcessor<N> {
    pub const fn new(config: VocalEffectsConfig) -> Self;
    pub fn process(&mut self, input: &mut [f32; N], carrier: Option<&[f32; N]>,
                   settings: &MusicalSettings, output: &mut [f32; N]);
}
```

- Still zero-allocation and `no_std`: the caller decides placement (a `static`, an RTIC
  local, a `#[link_section = ".dtcm"]`, or a `Box` on desktop).
- Write into an output parameter instead of returning `[f32; N]` by value — the current
  return-by-value copies up to 16 KB per hop at N=4096.
- Keep the low-level free functions as a `raw` module if the split-task RTIC pattern
  needs them, but document the struct as the front door.
- Between the processor and `raw`, expose a curated `blocks` layer of composable
  spectral primitives (STFT bookends, envelope ops, bin shifting, vocode core) and
  rebuild the four modes on top of it — see api-spec.md §6. This is what turns the
  crate from "an autotune effect" into a vocal DSP toolkit.

## 2. Add a streaming layer

Today every consumer must reimplement the STFT plumbing: hop counting, `block_from`
unwrapping, overlap-add via `write_overlapped_samples` (the Synthphone firmware carries
all of this in `handler.rs`). That's the least portable part of the current design.

Offer a push/pull wrapper that owns the ring buffers and hop logic:

```rust
pub struct StreamingProcessor<const N: usize, const BUF: usize> { ... }
// feed arbitrary-size blocks in, get processed samples out
sp.write(&input_block);
sp.read(&mut output_block); // true when a hop was processed internally
```

This is what makes "works on desktop" real: a CPAL callback or a plugin `process()` can
feed it whatever block size the host uses. The Daisy firmware becomes a thin consumer of
the same API instead of owning the plumbing.

## 3. Fix the feature-flag design

Features must be additive in Cargo; the current set has several issues:

- `embedded` (default) is empty and `std` acts as its alternative — remove `embedded`
  entirely. Make the crate `no_std` by default; `std` only adds `std::error::Error`
  impls and conveniences.
- `cepstral-smoothing`, `formant-shifting`, `debug-logging` are declared but there is
  **zero** `cfg(feature = ...)` for them in `src/` — dead flags. Wire them up or delete
  them before 1.0 (deleting is a breaking change later).
- `debug-logging` doesn't enable the optional `log` dependency (`debug-logging = []`
  should be `debug-logging = ["dep:log"]`) — symptom of the above.
- The ring buffer branches on `std` / `cortex-m` / neither with three different
  synchronization behaviors (`advance_write`, `latest_block`). Use the
  `critical-section` crate unconditionally as the portability layer, or better, remove
  the critical sections: for a true SPSC buffer, producer-only read-modify-write of the
  write index needs no critical section at all (see §4).
- Consider `portable-atomic` if targets without native atomics (thumbv6m, some RISC-V)
  are ever in scope.

Target matrix for CI (see §7): `--no-default-features`,
`--no-default-features --target thumbv7em-none-eabihf`, `--features std`, `--all-features`.

## 4. Ring buffer: enforce SPSC at compile time

`RingBuffer` is sound only under single-producer/single-consumer discipline, enforced by
a comment and an `unsafe impl Sync`. For a public 1.0:

- Split into `Producer<N>` / `Consumer<N>` handles (the `heapless::spsc` / `rtrb`
  pattern) so misuse doesn't compile.
- Define overflow/underflow semantics deliberately: `push` currently overwrites unread
  data silently and `pop` returns 0.0 on empty. That's a reasonable audio choice
  (glitch, don't block) but document it as such, or return `Option`/counts and let the
  caller decide.
- `advance_write`'s interrupt-free sections are unnecessary under SPSC (only the
  producer touches the write index) — removing them deletes the entire `cfg` ladder.
- Decide whether the ring buffer is part of this crate's public API at all, or an
  internal detail of the streaming layer (§2). Smaller public surface = easier 1.0.

## 5. Config and settings hardening

- `VocalEffectsConfig` has all-pub fields, so `new()`'s validation is advisory —
  `hop_size` can disagree with `fft_size * hop_ratio`, and `config.fft_size` is never
  checked against the `N` of the function you call. Tie the config to the processor's
  const generic (`VocalProcessor::<1024>::new(config)` errors if
  `config.fft_size != 1024`), and either make fields private with getters or mark the
  struct `#[non_exhaustive]` so fields can be added post-1.0.
- `MusicalSettings` uses magic integers (`key: i8` 0–23, `note: i8`, `formant: i8`
  0/1/2). Replace with enums (`Key::CMajor`, `FormantMode::{None, Male, Female}`) —
  self-documenting and invalid states unrepresentable. `midi_frequencies: [f32; 8]`
  hardcodes the Synthphone's 8 voices; make it a slice or const-generic.
- `VocalEffectsError` has variants nothing returns (`BufferSizeMismatch`,
  `ProcessingFailed`). Trim to what's used, or make `process` fallible where it should
  be.

## 6. Math policy

- Both `micromath` and `libm` are dependencies; usage is mixed (e.g. `libm::sinf` per
  sample in `Oscillator::next_value`). Pick one policy and centralize in `math.rs`:
  a single internal `sin/cos/exp/ln` facade, with an optional feature (or `std`) to
  route to faster/more-precise implementations per platform.
- The oscillator's per-sample `libm::sinf` is the slowest reasonable choice on
  Cortex-M — a wavetable or polynomial approximation fits the crate's embedded-first
  positioning (the Synthphone firmware already ships a Bhaskara sine for drums; the same
  trick works here).

## 7. Docs, packaging, CI — required before publishing

- **README is currently wrong**: the example uses an invalid crate name in the `use`
  statement (hyphens), calls `process_vocal_effects_1024` with an outdated 7-arg
  signature, references a nonexistent `ProcessingMode::Autotune`, and shows version
  0.0.1 vs the manifest's 0.1.1. Make the README example a doctest (or an `examples/`
  file compiled in CI) so it can never rot again.
- Add `examples/`: a host-side demo (hound: WAV in → autotuned WAV out) and a live CPAL
  mic passthrough. These *prove* the platform-agnostic claim and double as integration
  tests.
- Crate name: **decided (2026-07)** — stays `synthphone-e-vocal-dsp`. The Synthphone is
  the primary use case; platform-agnosticism is a property of the crate, not its name.
- CI (GitHub Actions): fmt + clippy, host tests, `cargo build --no-default-features
  --target thumbv7em-none-eabihf` (the real embedded guarantee), doc build with
  `--all-features`, and the feature matrix from §3. Post-1.0, add `cargo semver-checks`.
- Golden-audio regression tests: check in short WAV fixtures, process them in CI, and
  compare against reference output within tolerance — this is the only test style that
  catches DSP regressions (phase bugs, envelope glitches) that unit tests miss.
- Criterion benches per mode × FFT size, tracked over time, since "fits in the hop
  budget on a 480 MHz M7" is the crate's core promise (at 1024/256 @ 48 kHz that budget
  is 5.3 ms per hop).

## 8. Hardcoded-values audit

Magic numbers currently baked into the processing paths, grouped by what should happen
to them in V1. (File:line references are as of commit `2d33801` + in-flight changes.)

### 8a. Config fields that exist but are silently ignored

The inverse problem — worse than a hardcode because callers believe they're tuning
something:

- `config.pitch_correction_strength` (default 0.999) and `config.transition_speed`
  (default 0.1) are **never read** by any processing path. `calculate_pitch_shift`
  hardcodes its own `SMOOTHING_FACTOR = 0.99` (`signal_processing.rs:87`) instead.
  The only consumer of `transition_speed` is `calculate_updates`
  (`frequency_analysis.rs:8`), which is itself dead code — nothing calls it
  (`collect_harmonics` is dead too). Fix: wire `pitch_correction_strength` into
  `calculate_pitch_shift`, drop `transition_speed` or give it a real consumer, delete
  the dead functions.

### 8b. Should be per-instance configuration (`ProcessorConfig` in the API spec)

- **Soft-clip limiter**: threshold `0.95`, knee `0.05`, exp shape — copy-pasted three
  times (`effects/mod.rs:159, 517, 698`). Belongs in config (`limiter_threshold`,
  possibly on/off); at minimum deduplicate into one named function.
- **PitchShift synth mix**: `vocals * 0.96 + synth * 0.04` (`effects/mod.rs:360`) — a
  hardcoded wet/dry blend that makes the carrier barely audible and isn't adjustable.
- **Pitch-shift smoothing**: `SMOOTHING_FACTOR = 0.99` (see 8a — becomes
  `pitch_correction_strength`).
- **Harmony envelope refresh cadence**: `ENVELOPE_UPDATE_PERIOD = 16` hops ≈ 85 ms
  (`effects/mod.rs:599`) — a latency-vs-CPU tradeoff the integrator should own.
- **YIN vocal range**: `MIN_VOCAL_HZ = 80.0`, `MAX_VOCAL_HZ = 600.0`
  (`frequency_analysis.rs:140-141`) — intentionally narrower than
  `config.min/max_frequency` (which drive HPS only), but bass singers and children
  exist. Belongs in `PitchDetectorConfig` alongside the YIN `THRESHOLD = 0.15` and the
  `0.5` aperiodic-rejection fallback.
- **PitchShift bypass window**: pitch ratio in `0.99..1.01` short-circuits to
  pass-through (`effects/mod.rs:277`).

### 8c. Values that silently assume N = 1024 or a fixed sample rate

These are *correctness* bugs at other FFT sizes, not just inflexibility:

- `DEC_BUF = 128` in YIN is literally commented "1024 / 8"
  (`frequency_analysis.rs:135`). At N = 512 only half the decimated buffer is filled
  (min_lag/max_lag math still uses the full 128 assumption); at N = 2048/4096 the input
  is truncated to the first 1024 samples. Should derive from `N / DECIMATION`.
- `LIFTER_CUTOFF = 64` quefrency bins (`signal_processing.rs:12`): the cepstral
  smoothing bandwidth this represents scales with N and sample rate — 64 bins at
  N = 512 is a very different formant envelope than at N = 4096. Should scale with N
  (e.g. `N / 16`) or be config.
- `ENV_W = 16` bins for the harmony envelope's moving average (`effects/mod.rs:605`):
  same issue — 16 bins is ~750 Hz at N = 1024/48 kHz but ~187 Hz at N = 4096. Define in
  Hz, convert via `bin_width`.
- `SMOOTH_BINS = 8` in `extract_simple_envelope` (`signal_processing.rs:54`): same
  bins-vs-Hz confusion.

### 8d. Synthphone-specific encodings that must not ship in a general library

- **Octave encoding** `octave as f32 * 0.5` (`effects/mod.rs:81, 273`): the octave
  setting only makes sense with the firmware's 1/2/4 values (→ ×0.5/×1.0/×2.0). The
  API-spec's `octave_shift: i8` (semitone-free ±octaves, factor `2^shift`) replaces it.
- **`get_frequency(key, note, octave, is_vocoder)`** (`keys.rs:160`): the
  `octave_idx` match on `1|2|4` with a vocoder-dependent row offset is keypad-layout
  logic — the comments literally say "first row/second row". Move to the firmware;
  the library exposes `note_frequency`/`scale_frequencies` only.
- **Autotune target priority**: `settings.midi_frequencies[0]`
  (`signal_processing.rs:75`) — "first MIDI voice wins" is a Synthphone policy;
  should be an explicit `target: Option<f32>` in settings.
- **Phase-array smuggling**: the previous YIN frequency and the harmony hop counter are
  stashed in `last_input_phases[HALF_N + 1]` and `[HALF_N + 2]`
  (`effects/mod.rs:395, 598`) — clever, but it only works because callers pass
  oversized `[f32; N]` phase arrays. Becomes ordinary named fields once
  `VocalProcessor` owns its state (§1).

### 8e. Fine as constants, but name and centralize them

Numerical guards, currently scattered and inconsistent: envelope floor `1e-6`
(4 sites), bin-skip gate `1e-8` vs `config.magnitude_threshold` (`1e-6`) used for the
same purpose in different modes, vocoder carrier gate `1e-4`
(`effects/mod.rs:209`), YIN silence gate `1e-8`, voiced-detection gate `0.001`
(2 sites), envelope-extrapolation decay clamp `0.05..1.0`. Also the harmony octave-snap
fold windows `1.65..2.5` / `0.38..0.6` (4 sites across the two harmony functions) —
algorithm constants, but they should exist exactly once with the derivation documented.

Tuning reference is also implicit: `BASE_FREQUENCIES` starts at C0 = 16.35 Hz, i.e.
A4 = 440 Hz equal temperament (`frequencies.rs:7`). Fine as a default, but a
`reference_pitch_hz` (A4) in config is cheap and standard practice (orchestral 442,
baroque 415).

## Suggested order

1. Commit/land the in-flight `effects/` changes.
2. §3 feature cleanup + §7 CI (cheap, protects everything after).
3. §8a fixes (wire up or delete the dead config fields — quick, and callers are
   currently being lied to) and §8c fixes (correctness at non-1024 FFT sizes).
4. §1 processor struct (breaking change — do it once, early).
5. §5 config/settings hardening + §8b/§8d/§8e promotion of hardcoded values (rides
   along with §1's API break).
6. §2 streaming layer + desktop examples.
7. §4 ring buffer split, §6 math policy.
8. README/docs rewrite, golden tests, then publish 1.0.
